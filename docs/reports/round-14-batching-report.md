日期:2026-08-03 · 還原點 commit `490abf6` (`batching-only restore point`)

### 步驟 1 — 詛咒符文陣 → 貼圖(`Tower.gd`)

舊版每座詛咒塔每幀畫返晒出嚟:兩隻碟 + 一個 52 段嘅弧 + 兩圈共 13 條線 13 粒點
+ 一粒金點 ≈ 90 個 primitive。**喺 Godot 嘅 2D renderer 入面 polygon 批唔埋**
(只有矩形先批得埋),所以嗰 90 個基本上就係 90 個 draw call。

而家:

* 兩隻碟 → 一張 `fx/curse_haze.png`。實心碟按比例縮放係**完全準確**嘅
  (冇線寬呢個問題),所以一張圖服務得晒所有射程。
* 13 粒符文 → 13 個 `Sprite2D`,擺喺兩個**只係郁 `rotation`** 嘅 `Node2D` 入面。
* 金點 → 一個 sprite,郁 `position` / `modulate`。
* 外圈嗰個脈動光環 → **仍然係一條真 `draw_arc`**,但只畫一次,脈動改為郁
  `modulate.a`。點解唔烘做貼圖:嗰條線係固定 3px 闊,而詛咒塔嘅射程係課得上去嘅,
  一張烘死嘅光環貼圖會跟住射程變肥。一個弧一個 draw call,而場上詛咒塔數得出,
  呢個代價買返一個**完全一樣**嘅外觀。

一座塔:~90 個 primitive → 15 個 sprite + 1 個弧,而且**一句 `queue_redraw()`
都冇** —— 旋轉同脈動都係 node property,唔會令 CanvasItem 變 dirty。
15 個 sprite 共用同一張圖,所以合埋一個 batch。

符文陣嘅 `z_index` 由「塔嘅 canvas item 自己畫」變成相對 −1(即實際 z 14),
咁全場所有符文陣落喺同一個 z 桶,批得埋。

### 步驟 1b — 聖光光點 → 一個 MultiMesh(`Battle.gd`)

舊版**每座塔**(唔只聖光塔)喺自己 `_draw()` 畫三粒繞行金光 = 43 座 × 6 個圓
= 258 個 primitive,而且要 43 次 `queue_redraw()` 一幀。

三粒點嘅半徑、顏色、透明度全部由**一個全場數**(`holy_haste_total +
holy_power_total`)決定,即係成場所有光點一模一樣,淨係位置唔同 —— 教科書
MultiMesh 情況。而家全場一個 `MultiMeshInstance2D`,**一個 draw call**。
聖光塔本體嗰條光柱剩返兩個 sprite(`fx/holy_pillar.png` + `fx/holy_core.png`),
郁 `scale` / `modulate`。

### 步驟 2 — Fx 改造(`FxRender.gd` 新寫,`Fx.gd` 唔再畫嘢)

`Fx` 由「一個識畫自己嘅 node」變成**一件數據**(種類、位置、顏色、壽命)。
真正嘅畫集中喺 `FxRender`,佢每幀行一次全部 live 嘅 fx 砌成幾層:

| fx 種類 | 新畫法 | draw call |
|---|---|---|
| SPARK(火星) | 兩層 MultiMesh(染色本體 + 白色高光) | 2 |
| SPARK diamond(金幣) | 兩層 MultiMesh | 2 |
| BURST(爆炸) | 本體 / 白核 / 碎片棒 三層 MultiMesh | 3 |
| ORB(氣團) | 一層 MultiMesh | 1 |
| RING(衝擊波) | 三條 `draw_multiline`(線寬固定 11 / 5 / 2) | 3 |
| LINE(閃電 / 光束) | 按線寬分桶嘅 `draw_multiline` | ~10 |

兩個關鍵手法:

* **顏色由 instance color 帶,貼圖淨係帶形狀同相對 alpha。** 例如爆炸嘅煙圈
  原本係 `Color(col.r*0.35, col.g*0.30, col.b*0.30, a*0.42)` —— 貼圖嗰個像素就
  烘 `(0.35, 0.30, 0.30, 0.42)`,乘上 instance color `(col.rgb, a)` 之後同原式
  一模一樣。一張貼圖服務得晒所有顏色嘅爆炸。
* **圓環唔烘貼圖,用 `draw_multiline`。** 三層嘅線寬係固定嘅(11/5/2),郁嘅
  只係半徑,而一個環喺自己一生入面半徑會脹大四倍 —— 烘咗貼圖再放大就連線寬
  一齊放大。`draw_multiline` 將所有線段砌成**一個** polygon command,所以三個
  固定線寬 = 三個 draw call,畫幾多個環都係三個,而且幾何同 `draw_arc(...,32,...)`
  逐點對逐點一樣。冇用 shader:網頁版係 GL 相容渲染器,少一個 shader 就少一個
  「喺我部機得、喺你部機唔得」嘅風險。

### 步驟 3 — 怪物資訊層集中畫(`MonsterOverlay.gd` 新寫)

舊版每隻怪喺自己 `_draw()` 畫自己條血條。表面睇一條血條得兩個 `draw_rect`,
但佢同佢個 sprite 子節點喺 render list 度係**梅花間竹**排嘅:

```
怪1 血條 → 怪1 sprite → 怪2 血條 → 怪2 sprite → ...
```

每次由「矩形」轉去「貼圖」都斷一次 batch。而家血條全部喺一個 node 一次過畫晒
(連續嘅 `draw_rect` 批得埋),詛咒印改成一層 MultiMesh,詠唱環都搬埋過去 ——
`Monster` 而家**完全冇 `_draw()`**,所以所有怪物 sprite 喺 render list 度變成
連續一段,atlas 先至有嘢批得到。`queue_redraw()` 亦都由每幀 143 次變成 1 次。

### 步驟 4 — 傷害數字 → 一個 `draw_string` 場(`DamageField.gd` 新寫)

`DamageNumber` 由 `Label` 變成一件數據,全場數字喺一個 CanvasItem 用
`draw_string()` 畫。淡出由 item `modulate` 改成傳去 `draw_string()` 嘅顏色參數;
彈出由 item `scale` 改成**字級**,而字級量化到幾格再按格分組畫(同一字級 =
同一張字型圖集 = 一個 batch)。

量化嘅係「比原本大咗幾多」而唔係字級本身 —— 直接量化字級嘅話,彈完停低嗰個
字級會由 46 變成 48。

### 步驟 5 — Texture atlas(`gen_art.py` 嘅 `gen_atlas()` + `Assets.gd`)

`gen_art.py` 收工前將細圖砌成兩頁 + 一張座標表 `atlas_map.json`:

| 頁 | 尺寸 | 格數 | 填充率 | 入面有乜 |
|---|---|---|---|---|
| `atlas_battle` | 768×886 | 148 | 79% | 怪物 60、塔 60、特效 15、地面裝飾、傳送門、基地、士兵 |
| `atlas_ui` | 384×492 | 67 | 76% | 魔法圖示 45、介面圖示、徽章、金幣、魔晶 |

`Assets.gd` 只喺 `_load()` 入面轉一個彎:表入面有就返一個 `AtlasTexture`,
冇就照舊 load 原檔。**三十幾個呼叫端一個字都唔使改。**

三個決定:

* **分組跟「同時上畫」唔係跟資料夾。** 金幣同魔晶本來擺咗入 battle 頁,實測
  一入主選單就為咗一粒 40px 嘅圖示載入成頁戰鬥圖,texture memory 多咗 2.6MB。
  搬去 ui 頁之後主選單返返正常。
* **平鋪嘅嘢一定唔可以入**:`tiles/ground`(`texture_repeat`)同 `tiles/road`
  (Line2D 平鋪)—— 入咗就會連隔籬格一齊鋪。
* **每格四邊向外擠出 2px**。`texture_filter=NEAREST` 加上鏡頭縮放(0.5x–2x)
  之後取樣點會落喺格邊,擠出之後滲出嚟嘅係自己嘅邊唔係人哋嘅身。
  逐像素驗證結果:**完全零差異**(見第 5 節)。

新增 `test/AtlasTest.tscn`(208 張貼圖)守住呢件事:應該入 atlas 嘅有冇靜靜跌返
落原檔、唔應該入嘅有冇入咗。佢已經抓咗一個真 bug:「檔名尾係 9 就當 9-patch」
呢條規則掃全場嗰陣順手剔走咗 `tower_9` / `tower_19` / `spell_9` 三張普通圖。

## 4. 稜鏡塔假說 —— 成立,而且係兩個原因

上輪假說:3x 之下 fx 生成 ×3,pool 打正 400 上限,`spawn_line()` 喺 pool 滿嗰陣
靜靜 `return`,所以光束消失。

`tools/prism_probe.tscn`(新寫)重現嗰個情境:17 座稜鏡塔 + 26 座火星大戶
(機槍 / 加農 / 閃電 / 磁力)、130 隻怪、3x、每 0.6 秒放一個魔法,跑 10 秒。

| | 改造前(舊策略) | 改造後(新策略) | 改造後(同一 build,關咗徵用) |
|---|---|---|---|
| `spawn_line` 被拒次數 | **90** | **0** | 95 |
| 爆炸被拒次數 | 127 | 0 | 143 |
| 火星被拒次數 | 547 | 576 | 579 |
| 徵用(recycle)次數 | — | 326 | 0 |
| fx 池峰值 | 400(打正上限) | 400 | 400 |
| **折射光束睇得見嘅幀比例** | **6.6%** | **99.0%** | 99.0% |
| 10 秒入面總幀數 | 517 | 1361 | 1352 |

**假說成立**:pool 真係滿,而 `spawn_line` 真係每秒被靜靜拒絕大約九次。

但量完之後發現**仲有第二個原因,而且佢先係大頭**:一條光束嘅壽命係 0.05
遊戲秒,3x 之下即係 **16.7 毫秒真實時間**。而改造前高峰戰鬥嘅幀時間係
16.43ms 平均 / 23.58ms p95 —— 即係話**一條光束成條命都塞得落一個幀縫入面**,
生咗、死咗,一幀都冇畫過。呢個解釋咗點解「傷害正常但睇唔到光束」。

證據就喺表入面最後兩欄:同一個改造後嘅 build,關返徵用策略(即係回復舊嘅
靜靜拒絕),折射光束一樣係 99% 睇得見 —— 因為幀時間已經由 16.4ms 跌到 5.1ms,
一條 16.7ms 嘅光束而家一定跨到兩三幀。

### pool 滿嘅靜默失敗:徵用策略

`Battle._fx_take()` 而家喺 pool 滿嗰陣**徵用最早派出去嗰個特效**,而唔係靜靜
唔畫。點解揀「最早派出」:`Pool` 用 `Dictionary` 記住派出去嘅 node,而 Godot 嘅
Dictionary 保住插入次序,所以攞第一個 key 就係最舊 —— O(1),唔使排序四百個。
最舊嗰個一定係場上最接近死亡嗰批之一,而「一個舊裝飾早零點幾秒消失」肉眼睇唔出,
「主攻擊冇咗」睇得出。

火星同金幣**唔會**徵用(佢哋本來就係「場面夠亂就慳返」嗰批,見 `_spark_allowance`),
所以表入面火星嘅被拒數冇跌 —— 嗰個係設計,唔係漏。

順手加咗 `Battle.fx_rejected` / `fx_recycled` 兩個計數器,令「特效預算爆咗」
由一件睇唔見嘅事變成一個量得到嘅數。

## 5. 外觀驗證

`tools/fx_shots.tscn`(新寫)喺一個 1080×1920 SubViewport 入面砌 29 個**確定性**
畫面:固定 seed、固定機位、`get_tree().paused = true` 之後自己逐幀叫
`_process(1/60)` —— 所以「第 12 幀」喺兩個 build 入面係同一個 12 幀,同實際幀率
無關。動畫類(符文旋轉、光點繞行、fx 生命周期)每個影三個時點,唔係淨係比一張
靜態圖。

再用 `tools/shot_diff.py` 逐像素比。

**逐個解釋有差異嗰啲:**

1. **`fx_burst`(最大)** —— 爆炸嘅五嚿火本來係逐個 instance 隨機抖出嚟嘅,而家

   (以前固定 3px),所以一個好大嘅爆炸個邊會粗少少。
2. **`damage`** —— 大字嘅水平位置差最多 5px(`draw_string` 嘅基線計法同

## 6. Atlas 對 pck 體積同 VRAM 嘅影響

**pck 體積**:7,072,032 → **7,228,980 bytes(+153 KB,+2.2%)**。

| 群組 | before | after | 差 |
|---|---|---|---|
| `.godot/imported`(全部貼圖 + 音效) | 1702.7 KB | 1819.8 KB | +117 KB |
| `scripts` | 303.5 KB | 316.1 KB | +12.6 KB |
| `assets`(`.import` 描述檔) | 54.0 KB | 71.7 KB | +17.7 KB |
| `(root)`(`icudt_godot.dat` 4.7MB) | 4688.0 KB | 4688.0 KB | 0 |
| **合共 payload** | 6837.6 KB | 6986.7 KB | +149 KB |

+117 KB 嘅貼圖入面:兩頁 atlas 大約 +100 KB、十五張新特效貼圖大約 +17 KB。

**點解冇將原本嗰批散圖剔出 pck**:入咗 atlas 之後嗰批散圖喺遊戲入面已經冇人
load,理論上可以由 `exclude_filter` 剔走再慳返大約 1.2MB。冇做,理由係
`Assets._load()` 嘅設計係「atlas 冇就 fallback 去原檔」—— 一剔走,任何一張
將來漏咗入 atlas 嘅圖就會由「多一個 draw call」變成「畫一嚿程序生成嘅色塊」。
+153 KB(2.2%)買一個唔會靜靜爆嘅出貨包,抵。`test/AtlasTest` 已經守住咗
「有冇圖跌返落 fallback」,將來想剔嘅話個安全網已經喺度。

**VRAM**:高峰戰鬥嘅 `RENDER_TEXTURE_MEM_USED` 由 7.70MB 升到 11.45MB
(+3.75MB)。因為我每一步都量咗一次,所以呢個 +3.75MB 拆得出:

| 步驟 | texture mem | 該步嘅增量 | 邊度嚟 |
|---|---|---|---|
| 原狀 | 7.70 MB | — | |
| 詛咒 / 聖光 / Fx 貼圖 | 8.91 MB | **+1.21 MB** | 15 張新特效貼圖(爆炸 256²、符文陣 256²、光柱 208×688 …) |
| 怪物資訊層 | 8.93 MB | +0.02 MB | 詛咒印貼圖 |
| 傷害數字 | 11.18 MB | **+2.25 MB** | 由 2 個字級變成 5 個,而 Godot 每個字級開一張自己嘅字型圖集 |
| texture atlas | 11.45 MB | **+0.27 MB** | atlas 兩頁 +3.4MB,但原本嗰批散圖唔再載入 −3.1MB |

**最貴嗰樣係字型圖集,唔係 atlas。** Atlas 淨增只係 0.27MB —— 佢基本上係
用 3.4MB 一次過換走 3.1MB 散圖。字型嗰 2.25MB 已經收窄過一次:大字嘅量化格
由 6 級放寬到 12 級,字級由 8 個收到 3 個。再收就會見到彈出動畫一格格跳。

**呢個 +3.75MB 值唔值**:換返嚟嘅係高峰戰鬥少 887 個 draw call、幀時間少
11.6ms。喺一部靠 tile-based GPU 嘅電話上面 draw call 係發熱嘅主因之一,而
3.75MB 喺一個大約 300MB 嘅 iOS Safari tab 預算入面係細數。**但呢個判斷要 Jack
喺真機驗** —— 見最後一節。

1. **發熱對比(本輪嘅終極驗收)。** 同一關、同一段時間、同一個速度,對比
   改造前後電話嘅發熱同耗電。呢一輪嘅整個理由就係「draw call 係 tile-based

2. **3x 稜鏡塔。** 光束塔升到第二階,開 3x 打一場滿場嘅。折射光束應該由頭到尾
   都見到,唔會再喺場面最亂嗰陣消失。
3. **外觀有冇睇得出唔同。** 三個重點位:
   * 爆炸(火嚿排法變咗,大細顏色冇變)
   * 傷害數字(大字嘅彈出而家係分三格,唔係連續)
   * 血條(而家永遠喺怪之上,唔會被隔籬隻怪擋住)
4. **記憶體。** 玩十幾關唔好熄 app,睇下有冇比以前更早跪。30 分鐘 soak 嘅
   曲線係平嘅(冇 leak),但**底線高咗大約 12MB / 8%**,而喺一部貼住 tab 上限
   嘅 iPhone 上面「平但高咗」同「會升」一樣可以整死佢。呢個係本輪唯一一個
   量到咗但答唔到嘅數。
