## 1. 麵包屑講到嘅嘢(唔使推論嗰部分)

38 條麵包屑,而環形 buffer 係 64 條 —— **冇滿過**,所以呢份係由開機到死
完整無缺嘅一條線,冇嘢被擠走。

`started:` 呢個欄位要小心讀:佢係 `_maybe_flush()` **每次寫檔嗰陣**填嘅
(`Crash.gd`),即係話佢係**最後一次 flush 嘅時間**,唔係開機時間。所以:

| | 換算 |
|---|---|
| 開機 | 12:55:51 − 3287.53s ≈ **12:01:04** |
| 切走(`web hidden`) | t=184.07 ≈ 12:04:08 |
| 切返(`web visible`) | t=3021.03 ≈ 12:51:25 |
| 最後一條麵包屑 | t=3287.53 = **12:55:51** |
| 下一次開機偵測到 | **12:56:12** |

即係話:

* 個 tab 喺背景**捱咗 47 分 17 秒**然後生還 —— 返嚟嗰陣 tick 由 3021 繼續,
  session 冇斷。**唔係**「iOS 掉走背景 tab」嗰個死法。
* 死喺**前景、玩緊嘅中途**,第三場連續嘅第 37 關,開場後 80.2 秒。
* 死完 **21 秒之內**個 tab 已經重新載入 —— 同用戶原話「閃退後自動重開」一致。

用第十一輪定低嘅判別式:最後一條**唔係** `web hidden`,而係玩緊嘅採樣
→ 唔係被系統掉走,係個 process 喺前景被殺(OOM 或者 renderer 死亡)。

**判別式嘅前一半成立咗。後一半 —— 「而 `mem` 曲線一路向上」—— 冇得驗證。**

## 2. 點解驗證唔到:個溫度計壞咗,而且壞成一個好合理嘅數

報告入面 30 幾個採樣,`static=` 每一次都係 `0.0MB`。同一行入面 video、obj、
node、fps 全部郁得好正常。

一個真係 0.0 MB 嘅 heap 冇可能。所以問題唔喺個遊戲度。

**量法**(`tools/mem_probe.gd`):同一份 code、同一部機、同一個引擎版本,
一次用 editor binary(debug)行,一次匯出成 Windows **release** template 行,
中間逐次分配 4 MB 落去。

| build | `MEMORY_STATIC` | 分配咗 12 MB 之後 |
|---|---|---|
| debug | 78.8 MB | 82.8 MB(跟得住) |
| **release** | **0** | **0**(一個字都唔郁) |

`Performance.MEMORY_STATIC` 喺 release export template 之下係硬編碼 0。
即係話**每一個出街版本**嘅閃退報告,`static=` 都係 `0.0MB`。

而 `Crash.last_crash_memory_trend()` parse 嘅正正就係 `static=`。

所以第十一輪特登起嗰條「用嚟分 OOM 定被系統掉走」嘅記憶體曲線,由第一日
出街開始就係**一條貼住零嘅平線**,而條平線喺報告畫面上面睇落同「記憶體
好平穩、唔似 OOM」**一模一樣**。

呢個先係要記低嘅一課:壞成一個 `n/a` 會即刻被人發現;壞成一個 `0.0MB`
會被人當成證據,然後收工。**一個假讀數比冇讀數更加壞。**

## 3. 修法:攞返一個喺出街版真係郁得到嘅數

網頁版可以攞到嘅 heap 就得一個 —— emscripten 嘅 **wasm linear memory**
(`engine.rtenv.HEAP8.length`)。wasm 嘅 memory **只增不減**,所以佢就係
「呢個 tab 喺作業系統手上面佔住幾多」,亦即係 iOS 殺 tab 嗰陣度緊嗰樣嘢。

排除咗嘅:

* `performance.memory` —— Chromium 專有,Safari 冇。iPhone 上面等於冇。
* `performance.measureUserAgentSpecificMemory()` —— 要 `crossOriginIsolated`,
  而 GitHub Pages 冇 COOP/COEP header。**喺真瀏覽器度量過:`false`。**

`Web.heap_bytes()` 有兩層 fallback,而且攞唔到就返 0 → 報告寫 **`n/a`**,
唔會再有一個扮數據嘅零。

### 驗證(唔係推論)

`tools/web_heap_probe.py` —— Playwright + Chromium,行**真正個 build**:

| 問題 | 答案 |
|---|---|
| `engine.rtenv.HEAP8` 攞唔攞到 | 攞到 |
| Godot 用嘅係 **indirect eval**(`engine` 係頂層 `const`,唔係 window property),見唔見到? | `typeof engine === "object"`,`100859904` |
| `crossOriginIsolated` | `false`(所以上面嗰條路真係唯一嘅路) |
| **全鏈路**:遊戲自己寫落 `user://logs/session.open` 嗰行係乜? | `heap=96.2MB video=24.0MB obj=1488 node=43 fps=1` |

最後嗰行係由 IndexedDB(網頁版嘅 `user://`)入面讀返出嚟嘅**遊戲自己寫嘅
麵包屑**,唔係喺瀏覽器度另外計一次。中間隔住 JavaScriptBridge、
`Crash.mem_line()` 同 IDBFS,三段都通。

**主選單靜止不動就已經 96.2 MB。** 呢個數由頭到尾冇出現喺兩份閃退報告入面,
而報告嗰陣寫住嘅係 `static=0.0MB`。

### 守門

`test/CrashWitnessTest.gd`(新,12 條斷言)。佢直接食**呢一份真報告嘅麵包屑
原文**,要求:條曲線抽得出、唔係平線、唔係全零、最後一點高過第一點、trend
講得出自己畫緊邊個數、而且 `mem_line()` 入面唔可以再有 `static=`。

呢條測試有牙:將 `static` 加返落 `TREND_KEYS` 就即刻 **4 條斷言爆**
(「條曲線係一條平線(全部 0.0)」)。呢個係特登驗過嘅 —— 第十一輪食過
一次假綠,唔想再嚟。

## 4. 條 video 曲線 —— 唯一一個真數,而佢係**有上限**嘅

報告入面唯一郁得到嘅記憶體數係 `video=`:31.3 → 55.4 MB,一次都冇跌返。
睇落好似漏,但量完之後結論係**唔係漏,係一個填緊嘅 cache,而個 cache 有頂**。

`Assets._cache` 係一個 autoload 上面嘅 Dictionary,載過嘅 texture 永遠唔放。
所以佢嘅上限就係「全部生成圖一齊常駐」:

| 資料夾 | 檔數 | RGBA8 |
|---|---|---|
| ui | 48 | **20.31 MB** |
| monsters | 60 | 0.63 MB |
| towers | 60 | 0.44 MB |
| spells | 45 | 0.33 MB |
| tiles | 13 | 0.16 MB |
| **合共** | **226** | **21.87 MB** |

UI 佔咗 93%,而入面又係得幾張:`menu_bg` 1080×1920 = **7.91 MB**,五張
`bd_*`(升級介面背景,1024×560)各 **2.19 MB**。呢啲喺 disk 上面得 9-21 KB
(PNG 壓得好靚),但喺 VRAM 入面係未壓縮嘅 RGBA8。

對得返報告:

* 同一個**升級介面**,前後兩次(t=30.41 / t=3197.51),`node=216` 完全一樣,
  但 video **+8.1 MB**。`bd_*` 係跟住揀中嗰件嘢嘅屬性換嘅 —— 玩家中間掃過
  幾件唔同屬性嘅塔,4 × 2.19 = **8.76 MB**,同量到嗰 8.1 MB 對得上。
* 三場戰鬥開場後 ~20 秒:obj 2594 → 2580 → 2568,node 571 → 520 → 514
  (**冇升**),但 video 49.0 → 50.8 → 54.4。即係話升緊嘅唔係場面上嘅嘢。

**所以 video 唔係兇手:佢嘅天花板係 ~22 MB texture + framebuffer,而 55.4 MB
已經行咗大半,再升唔到去一個殺得死個 tab 嘅數。** 呢個結論本身有用 ——
佢將注意力推返去嗰個由頭到尾冇量過嘅 heap 度。

## 5. 而家仲未知嘅嘢(講清楚,唔補鑊)

* **呢一單究竟係咪 OOM,答唔到。** 前景死亡 + 21 秒自動重載 + video 有升
  = 同 OOM 一致,但唔等於證明。唯一嗰個可以證明佢嘅數(heap)喺嗰個 build
  入面冇被記錄過。呢一輪嘅答案唔係「我修好咗閃退」,係
  **「下次再發生,份報告終於會有嗰個數」**。
* **WebGL context lost 分唔開。** 個 DOM overlay 喺頁面嗰邊彈,但 Godot
  嘅麵包屑寫唔低佢,所以一單 context 死亡同一單 OOM 喺麵包屑上面一樣係
  「斷喺半路」。要分得開就要 head_include 嗰邊寫一個標記入去,下一輪先做。
* **戰鬥中 fps 由 60 跌到 40**(node 爬到 ~1000,1x 速度,唔係 3x)。呢個
  同閃退未必有關,但喺一部 iPhone 上面係一個獨立嘅問題。
* **平衡**:連續三場第 37 關全部 `Fail`(殺 56/178、86/195),塔 55 / 43 座。
